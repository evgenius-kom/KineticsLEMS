# CLAUDE.md

## Project context

KineticsLEMS is a Python library + CLI (`kinetics-lems`) for isoconversional
kinetic analysis of thermal-analysis data (DSC, TGA, FSC, POM). Given a set
of experiments at different heating rates (or isothermal temperatures), it
computes the activation energy `E_a(alpha)` and, where applicable, the full
kinetic triplet `(E, A, f(alpha))`. Methods include Friedman, KAS, OFW,
Kissinger, Vyazovkin (1996/97 + AIC 2001), Criado-Malek Z(alpha) master
plot, Coats-Redfern, reaction-order sweep, jackknife uncertainty, ICTAC
consistency, compensation effect, lifetime / model-free prediction, and
arbitrary T(t) integration.

A "case" is a directory (or .zip of one) containing `settings.json` plus
plain-text wave files (2-column `T y` or 3-column `t T y`). `settings.json`
declares Material, ExperimentType (`heating` / `cooling` / `isothermal`),
Method (`DSC` / `TGA` / `FSC` / `POM`), and a `Conditions` map from
wave-file name to heating rate beta (K/min) or isothermal T (K).

Algorithm parameters live in TOML, the case description in JSON:
- `configs/default.toml`  - conversion grid, enabled methods, E search
  bracket, AIC window, output formatting. This is the *how to analyze*.
- per-case `settings.json` - material, rates, file map. This is the
  *what to analyze*. Override the TOML at runtime with
  `kinetics-lems analyze case/ --config my-config.toml`.

Source layout (paths are authoritative - read the file before claiming
behavior):

Units, conventions, and physical quantities (always check before doing
math - do not invent assumptions):
- Temperatures `T` are in Kelvin throughout the math layer. Settings
  files and reporting may use Celsius; conversion happens at the
  boundary.
- Heating rate `beta` is in K/min in inputs and reports, but the math
  layer converts to K/s where needed. Check the call site.
- Activation energy `E_a` is exposed in kJ/mol in the public API, CSV
  columns, and plots. Internally some integrals work in J/mol. Confirm
  the unit at the function boundary - never assume.
- Gas constant `R` lives in `constants.py`. Use it; do not redefine.
- Conversion `alpha` is dimensionless in [0, 1]. The conversion grid is
  controlled by `[conversion]` in `default.toml`
  (`step` / `min` / `max`).
- The Doyle approximation used by OFW lives in `constants.py` as
  `DOYLE_FACTOR`; do not hard-code numerics in method files.
- Method ordering matters: `preexponential` depends on `vyazovkin` +
  `master_plot`; `lifetime` depends on `preexponential`. Preserve the
  order in `[methods].enabled` when editing.

## Output layout

- Per analysis run, artefacts go under `out/<run_label>/` (default
  configured in `default.toml -> [output].directory`). Treat each
  generated dataset as a fresh subdirectory; do not silently overwrite
  prior runs.
- When generating outputs for a non-trivial parameter change (different
  conversion grid, different `ea_bracket_kJ`, vendor adapter swap,
  enabling Sestak-Berggren / Prout-Tompkins, etc.), the run label must
  encode the distinguishing change so the directory is
  self-documenting, e.g.:
    out/F1_120kJ/                              (default config)
    out/F1_120kJ_step0p02/                     (finer conversion grid)
    out/F1_120kJ_vyazAIC_da0p01/               (tighter AIC window)
- Each method writes its own CSV (`friedman.csv`, `kas.csv`, ...) and
  the orchestrator emits PNG + PDF plots side-by-side. Do not collapse
  these into a single file unless the user explicitly asks.
- `reporting_markdown.py` produces the single self-contained Markdown
  report that embeds every CSV + PNG + warnings + diagnostics. When
  adding a new method, also wire it into the markdown report - that is
  the user-facing summary.

## Long-running operations

- The biggest expenses in this repo are: Vyazovkin nonlinear integral
  (especially `vyazovkin_aic` with small `delta_alpha`), Coats-Redfern
  over all 12 models x runs, and full-suite pytest with reference
  workbooks. State the expected duration before launching anything
  heavier than a single-method run.
- For pytest runs targeting one method, use `pytest -q tests/test_<name>.py`
  rather than the full suite.
- Before re-running an analysis to apply specific parameter values
  (e.g. "regenerate with ea_bracket_kJ = [1, 800]"), check each
  requested value against the corresponding default in
  `configs/default.toml`. If every requested value already equals the
  default (and the previous run used those defaults too), DO NOT
  re-run. Tell the user the current output is already that
  configuration and ask what they actually want changed.
- For non-trivial code changes that affect the analysis pipeline, run a
  static check
  (`python3 -c "import ast; ast.parse(open('path/to/file.py').read())"`)
  and a `kinetics-lems --help` / `kinetics-lems analyze --help` smoke
  test BEFORE launching a full analysis or test suite. Catches typos
  in seconds instead of minutes.

## Core rules

1. **Ask, don't assume.** If something is unclear, ask before writing a
   single line. No silent assumptions about intent, architecture, or
   requirements. One concrete clarifying question beats five wrong
   steps.
2. **Simplest solution first.** Implement the simplest thing that could
   work. No abstractions, flexibility, or "future-proofing" that
   weren't explicitly requested.
3. **Stay in scope.** Only modify files / functions / lines directly
   related to the current task. Do not refactor, rename, reorganize,
   reformat, or "improve" anything not asked. If you notice something
   worth fixing elsewhere, mention it in a note at the end. Do not
   touch it.
4. **Flag uncertainty explicitly.** If you are not confident about an
   approach, fact, statistic, date, or technical detail - say so before
   including it. Never fill gaps with plausible-sounding information.
5. **ICTAC discipline.** When in doubt about kinetic methodology
   (multi-step decisions, beta spread, alpha range reliability,
   reporting requirements) defer to `docs/ALGORITHMS.md` and the ICTAC
   2011 / 2020 recommendations in `theory/`. Do not invent kinetic
   conventions.

## Behavior rules

- **Ask before big changes.** Before significantly altering content I
  have already created (rewriting sections, removing paragraphs,
  restructuring flow, changing tone, mass-renaming reporting modules):
  stop, describe exactly what you would change and why, wait for
  confirmation.
- **Confirm before destructive operations.** Before deleting files,
  overwriting existing code, deleting committed CSV / PNG references,
  dropping rows from reference workbooks, or removing dependencies in
  `pyproject.toml`: list exactly what will be affected and ask for
  explicit confirmation in the current message. "You mentioned this
  earlier" is not confirmation.
- **Hard stops** - require explicit in-session confirmation, no
  exceptions:
  - `git push`, force pushes, branch deletion on remote
  - Editing or deleting fixtures under `data/reference_workbooks/`
  - Re-generating xlsx-crosscheck tables (they are ground truth for
    tests)
  - Bumping version in `pyproject.toml` / cutting a release
  - Any command with irreversible side effects on the working tree
    (e.g. `git reset --hard`, `git clean -fd`)
- **Never act on the user's behalf** (publish, share, schedule emails,
  post issues, open PRs, push tags, anything outside this
  conversation) without explicit confirmation in the current message.
- **Think before code.** For architecture decisions, debugging tricky
  numerics (vyazovkin convergence, baseline drift, Z(alpha) shape),
  performance tradeoffs, or non-trivial features: work through the
  problem step by step before writing any code. Surface tradeoffs,
  identify uncertainty, flag assumptions that might not hold for
  multi-step / DAEM cases. Then implement.

  with the actual answer.

### Anti-hallucination

- Verify before claiming. Cite `file.py:line` or grep output for any
  claim about code (function name, flag, signature, behaviour). Do
  NOT invent API calls, library functions, CLI flags, config keys, or
  URLs.
- When the user states a fact you would have guessed differently (e.g.
  correcting a method's reference, a Vyazovkin formula, an ICTAC
  recommendation), verify against `docs/ALGORITHMS.md`, the source
  code, or the relevant PDF in `theory/` before accepting or pushing
  back. Don't auto-comply, don't auto-disagree.
- If a tool call output disagrees with your prior belief, trust the
  tool. Update the answer instead of explaining away the discrepancy.
- If you cannot do something the user asked for (missing data, wrong
  tool, environment limit) - say so directly. Do not produce a
  plausible-looking but fabricated result.
- Do not invent unit / scale assumptions. `E_a` is kJ/mol externally
  and may be J/mol internally; `beta` is K/min externally and often
  K/s internally; `T` is Kelvin in math, sometimes Celsius in I/O.
  State the unit convention you assumed and confirm against the
  function signature.
- Numerical methods (root-finding for Vyazovkin, Senum-Yang series for
  the temperature integral, Doyle approximation for OFW) have known
  convergence and applicability limits. Do not push them silently
  outside those limits to make a test pass; flag the limit instead.

## Conventions

- ASCII only - in code, comments, docstrings, identifiers, and string
  literals. Math / Greek symbols belong in docs (`docs/ALGORITHMS.md`,
  README tables, plot labels via matplotlib mathtext), not in source.
- Python >= 3.11 (uses `tomllib` from stdlib). Don't introduce
  dependencies outside `pyproject.toml`; if a new one is needed,
  surface it and wait.
- Line length 100, ruff selectors `E,F,W,I,B,UP` per `pyproject.toml`.
  Don't reformat unrelated files.
- Type-checked with pyright against the `.venv`. Keep type hints on
  public functions in `methods/` and `reporting*.py`.
- Plots: always go through `plotting.paper_style()` + `save_figure()`
  so DPI, font embedding, and PNG+PDF output stay consistent. Don't
  call `plt.savefig` directly in reporting modules.
- CSV column names are part of the public contract (tests parse them
  by name). Do not rename `alpha`, `Ea_kJ_per_mol`, `intercept`,
  `r_squared`, etc. without updating every reader and the README.
- Prefer the existing `io.read_case` /  vendor adapter scaffold over
  re-implementing parsing inline.

## Token efficiency

- `Read`: always pass `offset` + `limit` for files >100 lines. Find
  the line first with `grep -n`, then read the slice. Do NOT re-read
  a file already in context.
- `Bash`: pipe long output through `tail -N`, `head -N`, or
  `grep -E "..."` at call time. Never `cat` a large file or pipe a
  full log. If you don't know the size, do `wc -l` first.
- `Monitor`: narrow regex on terminal markers only
  ("PASSED|FAILED|ERROR|Saved"), never `tail -f` raw streams.
- For long jobs (full pytest, full-suite analyze) use
  `run_in_background: true` + `Monitor` with strict filter; do not
  poll.
- Parallelise independent tool calls in one message (multiple
  `Read` / `Bash` together) instead of sequential turns.
- Do not reuse `Read` to "verify" an `Edit` - Edit fails loudly if the
  change did not apply.
- Skip redundant exploration (`ls`, `git status`) when prior output
  is still valid.
- Prefer `Edit` over `Write` for partial changes. `Write` re-sends the
  whole file; `Edit` sends only the diff.
- Sub-agents (`Agent`) carry their own context overhead. Use only for
  genuine multi-step exploration that would pollute the main context,
  not for one grep.
- When asking the user a clarifying question, batch all related
  questions into ONE `AskUserQuestion` call, not sequential.
